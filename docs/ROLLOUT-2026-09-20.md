## ORDINE DI PUBBLICAZIONE

L'ordine non è indifferente, e la ragione è cambiata il 20/09: **prima il sito,
poi le Functions, poi le regole.**

- Il **sito per primo** perché le regole nuove filtrano l'elenco allenamenti, e
  la domanda che fa l'app di ieri viene rifiutata: più telefoni hanno già l'app
  nuova quando le regole arrivano, meno gente vede l'elenco vuoto.
- Le **Functions prima delle regole** perché `claimCompagnia` mette la compagnia
  nel token, e le regole nuove è quello che guardano per far vedere a un socio
  gli allenamenti «solo club» della sua compagnia. Se le regole arrivassero
  prima, quella parte resterebbe spenta per tutti fino al deploy delle Functions.

### 1. Il sito

```sh
git checkout main
git merge --ff-only risanamento-post-audit
git push origin main
```

`--ff-only` di proposito: se non passa, `main` si è mosso e va guardato prima.

**Cosa controllare** (GitHub Pages ci mette da uno a due minuti):

```sh
node tests/controlla-base.js       # tutti IN PARI
```

### 2. Le Cloud Functions

`pubblica.sh` clona il repository da GitHub: per questo il passo 1 viene prima.

```sh
bash ~/pubblica.sh                 # tutte e otto
bash ~/pubblica.sh claimCompagnia  # oppure una sola
```

**Cosa controllare.** Nella console Firebase → Functions devono comparire **otto**
funzioni, e `claimCompagnia` deve avere zero errori. Un modo veloce per vedere
che funziona: aprire l'app con un account che ha una compagnia, e guardare che in
`users/{uid}` compaia `claimApplicata` col codice della compagnia.

### 3. Le regole di Firestore

**Prima si salva quella che c'è adesso** (serve per il rollback, e dopo non si
recupera più dalla console):

```sh
git show main~1:firestore.rules > ~/regole-prima-del-20-09.rules
```

Poi: console Firebase → Firestore → Regole → incollare il contenuto di
`firestore.rules` (`2026-09-20-visibilita`) → **Pubblica**.

**Cosa controllare**, in quest'ordine:

1. l'app apre l'elenco allenamenti e non è vuoto;
2. un account **di una compagnia** vede gli allenamenti «solo club» della sua
   compagnia — se non li vede, è il claim: vedi «il token non arriva» qui sotto;
3. un account **di un'altra compagnia** non li vede (è il punto di tutto);
4. la scheda di una compagnia gestita mostra il referente al referente, e
   «chiedi di gestire» agli altri.

### 4. Il telefono in mano

`docs/STATO.md` §R2. Nessun banco sostituisce queste: push ad app chiusa, tocco
sulla notifica, orizzontale, Samsung con lo scuro forzato, avvio senza rete a
giro aperto, e che `arctrail3d.com/docs/` **non** risponda.

## Se qualcosa non va

### Se gli indici non sono READY

Le quattro domande dell'elenco allenamenti sono su **un campo solo**
(`visibility`, `clubCode`, `invitedUids`, `ownerUid`): Firestore li indicizza da
solo e non c'è niente da creare. **Se però compare un errore di indice**, si
riconosce così:

- nella console del browser: `FAILED_PRECONDITION: The query requires an index`,
  con un **link** che apre la console Firebase già compilata;
- l'elenco resta vuoto o incompleto, e **non** è un problema di permessi.

Cosa fare:

1. aprire il link dell'errore e premere **Crea indice**;
2. la costruzione richiede minuti (o ore, con molti documenti): finché lo stato è
   `Building`, quella query continua a fallire;
3. **non** è un motivo per tornare indietro sulle regole: l'indice e i permessi
   sono due cose diverse, e il rollback delle regole non farebbe comparire
   l'indice.

Se si vuole sapere prima come sta messo: console Firebase → Firestore → Indici →
la colonna **Stato** deve dire `Enabled`.

### Se il service worker non aggiorna

Sintomo: si è pubblicato, `controlla-base.js` dice IN PARI, ma sul telefono
l'app è ancora quella di prima.

Prima di toccare niente, ricordare come funziona: `sw.js` è l'unico file che il
browser rilegge **sempre** dalla rete. Se il suo contenuto è cambiato, il service
worker nuovo si installa; `CACHE_NAME` diverso fa buttare le casse vecchie. Quindi:

1. **`CACHE_NAME` è salito?** (`arctrail3d-v167`, contro `v166` online.)
   ```sh
   node tests/controlla-cache.js      # dice se la shell è cambiata senza alzare la cassa
   ```
   Se un file della shell è cambiato e la cassa no, il telefono continuerà a
   servire la copia vecchia **per sempre**: si alza `CACHE_NAME`, si rifà
   l'impronta (`node tests/controlla-cache.js --scrivi`) e si ripubblica.
2. **GitHub Pages serve ancora la copia vecchia?** Pages tiene `max-age=600`:
   fino a dieci minuti è normale. Si verifica dall'esterno, non dal telefono:
   ```sh
   curl -s https://arctrail3d.com/sw.js | grep CACHE_NAME
   ```
3. **Il telefono non ha ancora riaperto l'app.** L'aggiornamento si applica alla
   prima apertura con rete, e **non** durante un giro (è voluto: nessuna ricarica
   sotto il dito). Chiudere e riaprire l'app basta.
4. **Solo se serve davvero**, a mano sul telefono: Impostazioni del sito →
   Cancella dati. Si perde la cache, non i dati: giri e storico stanno in
   `localStorage` e su Firestore.

### Se il token non arriva (elenco «solo club» vuoto per i soci)

È la dipendenza dichiarata: le regole guardano `request.auth.token.compagnia`, e
ce lo mette `claimCompagnia`.

1. le Functions sono pubblicate? (passo 2)
2. in `users/{uid}` c'è `claimApplicata`? Se manca, il trigger non è mai partito:
   l'app lo sveglia da sola scrivendo `claimRichiesto` alla prima apertura in cui
   riceve il no;
3. l'app riprova **due volte per sessione** e poi smette, apposta: se dopo un
   deploy ancora non si vede, basta chiudere e riaprire.

Nessun intervento manuale è previsto. Se proprio si vuole forzare: cambiare
compagnia nel profilo e rimetterla.

## ROLLBACK

### Functions

```sh
git -C ~/at3d-repo log --oneline -5          # trovare la revisione di prima
cd ~/at3d-repo && git checkout <revisione>
firebase deploy --only functions --project arctrail3d
```

Oppure una sola: `firebase deploy --only functions:pushNotifica --project arctrail3d`.

**Cosa resta indietro**: i claim già scritti restano nei token. Non fanno danno —
se anche le regole tornano indietro, nessuno li legge. `claimApplicata` resta nei
documenti: è un campo in più, inerte.

### Rules

Il più veloce dei tre, ed è il motivo per cui vanno pubblicate per ultime:
console Firebase → Firestore → Regole → incollare
`~/regole-prima-del-20-09.rules` (salvato al passo 3) → **Pubblica**.
Ha effetto in pochi secondi, per tutti.

Se quel file non è stato salvato:

```sh
git show <ultimo-commit-prima-della-release>:firestore.rules
```

La console tiene anche una **cronologia** delle regole pubblicate, con la data:
si può ripescare da lì.

### Hosting (il sito)

Qui c'è una trappola, e va detta prima: **`CACHE_NAME` non può tornare
indietro.** Un telefono che ha già `v167` non prende `v166` come «nuova», e
`controlla-versioni.js` rifiuta una cassa che scende. Quindi non si torna
indietro: **si va avanti con dentro il codice di prima.**

```sh
git checkout main
git revert --no-commit <primo-commit-della-release>..HEAD
# poi, PRIMA di committare:
#   - in sw.js: CACHE_NAME = "arctrail3d-v168", CACHE_PARENT = "arctrail3d-v167"
#   - in app.html: BUILD_STAMP = "2026-09-20-ritorno", BUILD_PARENT = "2026-09-20-notturno"
node tests/controlla-cache.js --scrivi
node tests/controlla-versioni.js
git commit -m "revert: si torna al comportamento del 18/09 (cassa v168)"
git push origin main
node tests/controlla-base.js
```

Il numero sale anche tornando indietro: la cassa dice **quando**, non **cosa**.

**Ordine del rollback**: l'inverso della pubblicazione — prima le **regole**
(secondi, e sono quelle che possono chiudere fuori la gente), poi il **sito**,
poi le **Functions**, che da sole non fanno danno.

## Cosa si perde durante la finestra, e per quanto

Scritto prima, così non si scopre dopo. Tutto questo riguarda **solo** chi non ha
ancora aggiornato l'app, e finisce quando aggiorna (prima apertura con rete).

| cosa | da quando | per chi |
|---|---|---|
| l'elenco allenamenti resta vuoto | regole pubblicate | app di ieri |
| la scheda compagnia mostra «chiedi di gestire» anche se è gestita | regole pubblicate | app di ieri |
| la segnalazione di un campo non trova l'email del club | regole pubblicate | app di ieri |
| i soci non vedono i «solo club» della loro compagnia | regole pubblicate | tutti, finché il token non porta il claim |

Nessuna di queste perde dati. `tests/banco-finestra.js` le prova tutte e quattro
le combinazioni (app di ieri/oggi × regole di ieri/oggi) e dichiara quelle che si
perdono apposta.
